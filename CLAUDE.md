# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Fabric mod (Java 25) that runs inside Minecraft's JVM. It hides the vanilla HUD (health, hunger, XP, armor, hotbar) and streams that state every client tick over a loopback TCP socket, so a separate companion Android app can render it on a second screen. It also accepts short text commands back over the same socket (hotbar slot selection, simulated keybind presses, item-icon requests).

This mod is one half of a two-process system targeting the **AYN Thor** (dual-screen Android handheld) running Minecraft via **Zalith Launcher 2**. The other half — the Android companion app that renders the HUD — lives in a sibling repo, `Android_AynThor_MinecraftSecondScreen`. The two communicate only via the socket protocol; there's no shared code or build.

**`thor-hud-handoff.md`** is a detailed technical handoff/design doc covering the full system (both repos) — read it first for the JSON protocol spec, architecture rationale, and known issues. It's a snapshot from a point in development and may drift from the current tree in file/class specifics (there was a period of frequent package renaming) — verify anything file-specific against the actual source before relying on it.

## Commands

```
./gradlew build          # compile + package the mod jar
./gradlew runClient      # launch a dev Minecraft client with the mod loaded
```

Requires JDK 25. Uses Fabric Loom with `splitEnvironmentSourceSets()` enabled, so code lives in either `src/main` (both sides) or `src/client` (client-only — nearly all of this mod's logic lives here, since it's a client-only HUD mod). Versions (Minecraft, Loader, Fabric API) are pinned in `gradle.properties` — check there before assuming an API shape.

**Mappings: as of Minecraft 26.1, the game ships unobfuscated with Mojang's own names baked in — there is no Yarn mapping any more, and no `mappings` dependency in `build.gradle` at all.** This mod migrated off Yarn mappings when it ported from 1.21.11 to 26.2 (via Loom's `migrateMappings`/`migrateClientMappings` tasks, run while still on 1.21.11 before bumping the version, per Fabric's own migration guide). API names throughout this codebase are now Mojang's official names (`Minecraft` not `MinecraftClient`, `Player` not `PlayerEntity`, `client.gui.hud.getChat()` not `client.inGameHud.getChatHud()`, etc.) — the reverse of the assumption this section used to state. Class/method identifications made against 1.21.11 no longer apply verbatim; if a comment elsewhere in this codebase says "confirmed against decompiled 1.21.11", treat its *reasoning* as still sound but re-verify the exact API names against a `./gradlew genClientOnlySources` run for the current `minecraft_version` before relying on them literally — the 26.2 port needed real, non-trivial rendering-pipeline changes (see `ItemIconRenderer`'s history), not just a search-and-replace of class names.

Manual protocol smoke test (no Android app needed): run `runClient`, join a world, then from another terminal:
```
nc localhost 48291
```
You should see one JSON line per tick.

Scripted version, which is what to actually use — it auto-joins a world and dumps the whole protocol (assets, a HUD snapshot, map PNGs, bindings, chat) to disk:
```
./gradlew runClient -PquickPlay="New World"
python tools/capture_protocol.py --out captures
python tools/capture_protocol.py --out captures --say "hello"   # chat round trip
```
`--say` sends a `CHAT:` command and waits for the server's echo to come back as a chat line, which exercises both directions in one run. A leading `/` makes it a command, as in game.

## Architecture

Full protocol spec (message shapes, field meanings, command codes) is in `thor-hud-handoff.md` §2 — don't re-derive it from source when the doc already has it verified. In short: the mod broadcasts a full HUD snapshot (health/food/xp/armor/hotbar) every client tick (~20/sec, unthrottled) over `127.0.0.1:48291`, newline-delimited JSON. It replies to `ICON:<itemId>` requests with a base64 PNG, and accepts single-tick simulated key/hotbar-press commands as plain text lines.

**Why a socket, not shared memory:** the mod and the companion app run in separate Android app sandboxes (different processes/UIDs) despite being on the same device, so loopback TCP is the simplest channel available.

### Key classes (`src/client/java/com/exojosh/client/`)

- `GameHudVisibility` — decides per element whether the *game* draws its own HUD. **This is why the mod no longer calls `HudElementRegistry.removeElement()`:** removal is a one-way door, since the vanilla element's renderer belongs to vanilla and nothing is kept that could put it back. `replaceElement()` hands over the original and takes a wrapper that decides per frame whether to delegate; with nothing shown, that's behaviourally identical to the old removals. The companion app drives it — an element switched off on the second screen is handed back to the top screen, so between the two displays the HUD is drawn exactly once. Wire format is `HUD:<key>,<key>,…`, the **full set every time**, re-sent on every toggle and reconnect: a dropped or reordered delta would leave the two screens disagreeing about who owns an element, which shows up as one drawn twice or not at all. Keys must match `HudElement.key` in the app's `settings/HudSettings.kt`; `offhand` deliberately has no entry here, because vanilla draws the off-hand box as part of the hotbar.
- `ThorHudClient` — `ClientModInitializer`; installs `GameHudVisibility`'s wrappers, starts `HudStateServer`, and on each `ClientTickEvents.END_CLIENT_TICK` builds/broadcasts a `HudState` and drains inbound commands (routing `ICON:`-prefixed ones separately from action commands). `pushBundleToNewClients()` sends each new connection the texture bundle then the key bindings; both have to run on the client thread (resource manager, `GameOptions`/language files), which is why they're here and not on the accept thread.
**The HUD snapshot is sent on change, not every tick** (`broadcastHudStateIfChanged`). It used to go out 20 times a second forever, and almost all of those were byte-identical — nothing in the snapshot changes while a player walks around, since position isn't in it. Measured at 2 lines in 20 seconds idle against ~400 before. The last one is kept and handed to each new connection, or a client connecting to a stationary player would see nothing until they moved.

**The bind retries rather than giving up.** `acceptLoop` used to catch the `BindException` and *return*, killing the accept thread for the session — the second screen was dead until the game restarted, with nothing said anywhere the player looks. It now rebinds every 5s, so clearing a conflict is enough on its own. The failure goes to `System.err` **and** into the player's own chat in red, because this is the one error whose audience can't be reached the usual way: the second screen is the thing that isn't working. Every connection also opens with `{"type":"hello","mod":…,"protocol":N}`, written from the accept thread before anything else — a leftover `adb reverse tcp:48291` puts **adbd** on this port, and adbd accepts and instantly drops every connection, which the app otherwise reports as an ordinary flapping connection.

Leaving a world is reported as `{"type":"noplayer"}`, sent **once on the transition** via a `hadPlayer` latch in `ThorHudClient` — the tick loop used to just return early with no player, which left the second screen showing the last snapshot forever at the main menu. Repeating it per tick would be the same unthrottled broadcast the TODO still lists. The chat backlog is dropped with it, matching vanilla's `ChatHud.clear()` on disconnect. Note a full *quit* closes the socket before any further tick runs, so the harness can't observe this; the case it fixes is Quit to Title.

`HudState` also carries `gameMode`, `heartType` and `hardcore`. All three are sent **raw rather than pre-reduced** — the HUD decision belongs to whatever draws the HUD, same reasoning as air being sent in ticks. `heartType` follows `InGameHud.HeartType.fromPlayerState` including its precedence (poison → wither → freezing); `HudAssetCatalog` serves all seventeen heart sprites, because vanilla picks a *set* from the player and then a hardcore variant of that set from the world. The `*_blinking` pair of each is deliberately not served: that's the damage-flash animation, which is its own open item.

- `HudState` — record of one tick's snapshot; static `hotbarFromInventory(player)` and `offhandFrom(player)` builders over a shared `slotFrom(ItemStack)`. Carries `air`/`maxAir` (raw ticks and the current maximum, which Respiration raises above 300) for the companion app's bubble row — sent raw rather than pre-reduced to a bubble count, so the app applies vanilla's own rounding and no HUD decision gets baked into the wire format — plus `absorption` for golden hearts and `offhand` (a `HotbarSlot`, always present; an empty off-hand is `minecraft:air`, not an omitted field, because the app draws the box either way). All three postdate `thor-hud-handoff.md` §2's field list.

Note every element the second screen draws must have a `GameHudVisibility.Element` entry, `AIR_BAR` included; an element missing from that table is never wrapped, so the game keeps drawing it while the second screen draws it too.
- `HudStateServer` — owns the `ServerSocket`, one accept + one reader thread per client, `broadcast()`/`broadcastIcon()`/`broadcastAsset()`/`sendAssetTo()`/`broadcastBindings()`/`sendBindingsTo()`/`broadcastChat()`/`sendChatTo()`/`pollCommand()`/`pollNewClient()`. Writes are synchronized per-socket because the asset bundle is written to one client in a loop while `broadcast()` may be writing a state line to the same socket.
- `ContainerRelay` — the open screen handler's contents, and clicks back into it. **Streams `player.currentScreenHandler`, not `player.getInventory()`**, and that's the load-bearing choice: moving an item is not a write to the inventory, it's a *click on a slot*, and the server only honours those against the handler it believes is open. It costs nothing either, since with no container open `currentScreenHandler` already *is* the player's own inventory handler. Sent **on change**, not per tick — it's 46+ slots that are identical for minutes at a time, so the state is rebuilt each tick (cheap: a record of records) and only written on a difference; also replayed to each new connection, or a client that connects while the player stands still sees nothing until they next move something. **Slot roles are sent, not derived** (`playerStart`/`hotbarStart`/`armorStart`/`offhandIndex`): vanilla's "the player's 36 slots are the last 36" convention holds for every vanilla container, but knowing it is this side's job. `armorStart`/`offhandIndex` are -1 for anything but the player's own handler. Note `ScreenHandler.getType()` **throws** when the handler was built without a type, which the player's own inventory handler always is — `handlerTypeOf` guards it, and asking unguarded would blow up every tick the player isn't in a container. Clicks arrive as `SLOT:<syncId>,<slotId>,<button>,<ACTION>` and go through `ClientPlayerInteractionManager.clickSlot`; the syncId is a staleness check (a chest can close between the app drawing a slot and a finger landing, and "slot 3" then means something else entirely), refused *before* anything mutates rather than after, which is where vanilla's own check sits.
- `ChatRelay` — chat both ways. **Receiving** hooks Fabric's `ClientReceiveMessageEvents.CHAT` *and* `.GAME` rather than mixing into `ChatHud.addMessage`: they fire exactly where vanilla decides a message will be shown, so anything another mod suppresses never reaches the second screen either. CHAT is player messages, GAME is everything the server says (joins, deaths, `/say`, command output) — both are "chat" on screen; GAME with `overlay == true` is the action bar and is skipped. **The CHAT event's message arrives already decorated** (Fabric passes `MessageHandler.showMessageToPlayer`'s `decorated` local), so calling `params.applyChatDecoration` again would double the `<name>` prefix. Messages go out as `{"type":"chat","segments":[{"text":…,"color":…}]}` — flattened through `Text.visit(StyledVisitor, Style.EMPTY)`, which is what resolves style inheritance and expands translatable content into the player's language; `getString()` plus a hand-walk of `getSiblings()` would get neither. **Colour is the only styling kept**: it's the part that carries meaning in a log (team colours, a red death message), and the app draws from a bitmap font sheet where bold/italic/obfuscated would each need their own draw pass. A `HISTORY_LIMIT` of 100 (vanilla's `ChatHud.MAX_MESSAGES`) is replayed to each new connection from `ThorHudClient.pushBundleToNewClients`, after the asset bundle, since nothing re-sends chat on its own and an app restarted mid-session would otherwise come back to an empty log. **Sending** follows `ChatScreen.sendMessage` exactly: `StringHelper.truncateChat(StringUtils.normalizeSpace(…))`, then a leading `/` routes to `sendChatCommand` (argument signing, client-side dispatcher) rather than `sendChatMessage` — get that split wrong and "/tp …" is said out loud.
- `HudAssetCatalog` — **the app gets all its HUD textures *and its GUI chrome* from here**, pushed over the socket when it connects (`pollNewClient()` → `sendAssetTo()` in the tick loop; must be on the client thread because the resource manager is client-thread state). The app used to require users to hand-copy extracted textures into its assets folder; serving them means a fresh install just works, resource pack overrides come through for free (the resource manager already resolves the pack stack), and no Mojang assets sit in the app's repo. The wire format uses short stable keys (`heart_full`), not paths, so a version bump that moves sprites is a one-file change here and the app never knows. Paths verified against the 1.21.11 jar — note vanilla nests hearts under `heart/` but keeps armor and food flat with an underscore (`hud/armor_full.png`); that inconsistency is real, not a typo.
  - The catalog also serves **GUI chrome**: `widget_button`/`widget_button_highlighted`/`widget_button_disabled` and `container_slot`, which is what makes the app's tab strip, input grid and inventory cells the game's own controls. The three button sprites are nine-sliced, and their `.mcmeta` border is **3 for the two live states but 1 for `button_disabled`** — the app can't assume one number for all three. `container/slot` is a real 18×18 sprite since the 1.21.2 split, not something to crop out of `container/inventory.png`; there is deliberately no panel key, because vanilla has no nine-sliceable panel (its container background is a fixed 176×166 sheet whose interior is slots and a player portrait), so the app draws that itself from the same file's transcribed edge palette.
- `KeyBindingCatalog` — every key binding the game has, as data for the app's input picker (`{"type":"bindings"}`, pushed on connect beside the asset bundle and re-sent on a `BINDINGS` request). **This replaced two hand-maintained tables** — the app's grid of fixed codes and `CommandDispatcher`'s code→binding map — with one list that comes from the game, which is what stops them drifting apart again. Enumerates the **public** `GameOptions.allKeys`, not an `@Accessor` on `KeyBinding.KEYS_BY_ID`: same set (Fabric's key-binding API appends mod bindings into that array), no mixin. `id` is the wire identity and the binding's translation key; `label`/`category`/`boundKey` are translated here because only this side has the language files. It's a snapshot — a mid-session rebind pushes nothing, so `boundKey` can lag until the app re-requests; ids never go stale, so buttons keep working regardless.
- `CommandDispatcher` — maps letter codes to `KeyBinding`s and digit strings to hotbar slots.
  - **`BIND:<id>` is the current form**, resolved through the public `KeyBinding.byId`, and needs no table at all — another mod's binding works with no entry anywhere. The fixed `COMMANDS` codes are kept only for app builds that predate it, one disposal step behind the single-letter aliases. Hotbar taps go through the vanilla `hotbarKeys[]` binding rather than setting the inventory slot directly, so `MinecraftClient.handleInputEvents` keeps handling spectator mode, the creative toolbar modifiers, and server sync.
  - **Simulating a press needs both of a KeyBinding's states.** `isPressed()` reads a public `pressed` flag; `wasPressed()` drains a *separate, private* `timesPressed` counter that only the static `onKeyPressed` hook normally increments. Nearly every discrete vanilla action — hotbar selection, inventory, drop, swap-hands — reads `wasPressed()` and ignores the flag entirely, so the original `setPressed(true)`-only approach silently did nothing for any of them. `KeyBindingAccessor` (mixin) exposes the counter; `pressForOneTick` bumps it *and* sets the flag for one tick. Don't "simplify" this back to one or the other.
  - **Codes name actions, not keys** — `SWAP`, not `F`. They used to name keys and got it wrong (`R` bound to swap-hands, i.e. vanilla's F; `G` to drop, i.e. Q), and the app rendered the raw code as its button label, so the grid showed an R button doing an F key's job. Naming keys is a dead end regardless: attack and use are mouse buttons with no letter to borrow, and a player rebinding in-game invalidates the whole table at once. The old single letters (`E`/`R`/`G`/`H`/`K`/`F`) are kept as aliases with the behaviour they actually had, so an app built before the rename still works; delete them once both halves are known updated.
  - Vanilla only calls `handleInputEvents()` when `currentScreen == null && overlay == null`, so commands are **dropped** while a screen is open. Letting them queue instead would stack unconsumed presses that all fire at once when the inventory closes. **`CHAT:` deliberately doesn't come through here** — it's handled in `ThorHudClient`'s command loop beside `ICON:`/`ASSETS`/`HUD:`, because it's a packet rather than a `KeyBinding` press, so the screen-open guard's reasoning doesn't apply and a player with their inventory open should still be able to answer someone.
  - Timing: Fabric's `END_CLIENT_TICK` runs *after* that tick's `handleInputEvents()`, so a dispatched command is picked up on the next tick (~50ms). `tick()` must run before `dispatch()` each tick, which places the release after the game has read the flag.
- `ItemIconRenderer` — **the primary icon path.** Renders an item/block offscreen through the real vanilla model pipeline and reads it back as PNG bytes, so icons are isometric (vanilla's GUI display transform), use correct per-face textures, and work for composited/tinted/3D-modelled items. See "Offscreen icon rendering" below for how and why, and for the three real 26.2-porting bugs recorded there — none of them were mapping-name issues. **The glint is deliberately not rendered** — `suppressGlint` forces every layer's `FoilType` to `NONE` via `ItemStackRenderStateAccessor` before submitting. Letting the real glint through was an actual bug in both the 1.21.11 and 26.2 architectures (for different mechanical reasons, see below): an enchanted item came back as a flat square of glint texture with no item in it. The app draws the glint instead (`ui/ItemGlint.kt`), animated and masked to the item's alpha, from the `enchanted_glint_item` asset and the `hasGlint` flag the snapshot already carries.
- `ItemIconResolver` — legacy fallback only, used when `ItemIconRenderer` produces nothing. Resolves an item's raw texture PNG via `Minecraft`'s resource manager, with an `item/` → `block/` texture-path fallback. Structurally can't handle items whose icon isn't a single same-named texture file (`jungle_stairs` → `jungle_planks`, `stripped_birch_wood` → `stripped_birch_log`, multi-face logs, etc.), which is exactly what it used to render blank. **This is also what silently absorbed all three 26.2 regressions below** — every real-renderer failure fell back here, so single-texture items (sand, a plain plank) kept looking correct by coincidence while multi-texture ones (the crafting table) came back with nothing, which was the only visible symptom until the real renderer's own failures were found directly.
- `ItemStackRenderStateAccessor` (in `com.exojosh.client.mixin`) — `@Accessor` exposing `ItemStackRenderState`'s private `layers` array and `activeLayerCount`, added for the 26.2 port. `LayerRenderState.setFoilType` is already public; only the array holding the layers was private. Registered in `aynthor_secondscreen_v1_21.client.mixins.json`.
- `NativeImageInvoker` (in `com.exojosh.client.mixin`) — `@Invoker` exposing `NativeImage`'s private `writeToChannel(WritableByteChannel)` (renamed from `write` in 26.2) so icons can be PNG-encoded in memory instead of via a temp file. Registered in `aynthor_secondscreen_v1_21.client.mixins.json`.

### Offscreen icon rendering

Verified against decompiled 26.2 (`./gradlew genClientOnlySources`), not recollection — and not the 1.21.11 sequence this section used to describe. 26.2's rendering rewrite replaced the old immediate-mode `MultiBufferSource`/`ItemRenderer.renderItem` path with a two-phase submit/dispatch pipeline, and vanilla's own equivalent of this class is now `net.minecraft.client.gui.render.GuiItemAtlas` (the "UI items atlas" the 1.21.11-era note here already correctly guessed existed), which `ItemIconRenderer` mirrors closely enough that vanilla's source is the reference to re-check against, not this file, if the pipeline changes again:

1. `ItemModelResolver.updateForTopItem(state, stack, ItemDisplayContext.GUI, ...)` — bakes the real model into an `ItemStackRenderState`. `ItemDisplayContext.GUI` is what carries vanilla's isometric 30°/225° transform; this is the whole reason icons look like vanilla rather than flat textures.
2. Set `RenderSystem.outputColorTextureOverride`/`outputDepthTextureOverride` (unchanged public hook since 1.21.11) + an orthographic projection (`Projection`/`ProjectionMatrixBuffer`, replacing 1.21.11's `CachedOrthoProjectionMatrixBuffer`) sized to the icon, a scissor covering the whole icon texture (`RenderSystem.enableScissorForRenderTypeDraws`), and `Lighting.Entry.ITEMS_3D`/`ITEMS_FLAT` depending on `state.usesBlockLight()`.
3. `suppressGlint` forces every layer's foil off (see above), then `ItemStackRenderState.submit(...)` records the item into a `SubmitNodeStorage`, and `GameRenderer.featureRenderDispatcher().renderAllFeatures(...)` — the *same single call* `GuiItemAtlas` uses — turns it into actual draw calls. There is no per-command queue to hand-drain any more; that whole mechanism (`SubmitNodeStorage.ItemSubmit`, `MultiBufferSource`) doesn't exist in 26.2.
4. `CommandEncoder.copyTextureToBuffer(...)` for readback — same pattern as `ScreenshotRecorder`, but keeping alpha rather than forcing it opaque. **This is fenced and therefore asynchronous**, so the API is callback-based, not a return value. Reading the mapped result is now `GpuBuffer.map(read, write)` directly, returning a `GpuBufferSlice.MappedView` (1.21.11's `CommandEncoder.mapBuffer` no longer exists).

Nothing touches the real window framebuffer, so there's no on-screen flash on the primary display.

**Three real bugs surfaced porting this to 26.2, each with a distinct, non-obvious symptom — worth reading in full before touching this class again, since none of them threw an error that pointed at its own cause:**

- **Missing `GpuTexture.USAGE_COPY_DST`.** 26.2 added a hard requirement (`CommandEncoder.verifyColorTexture`/`verifyDepthTexture`) that any texture passed to `clearColorAndDepthTextures` has this usage flag, in addition to `USAGE_RENDER_ATTACHMENT`. Without it, every icon request threw `IllegalStateException: Color texture must have USAGE_COPY_DST` and silently fell back to `ItemIconResolver` — which is why this looked like a per-item bug (crafting table missing) rather than a total renderer failure: single-texture items' fallback happened to produce a plausible result.
- **Wrong call site.** 1.21.11's constraint was "render thread, no render pass open," which `END_CLIENT_TICK` satisfied. In 26.2, `GameRenderer.featureRenderDispatcher()`'s per-frame state isn't populated outside an actual frame's render pass, so calling this from tick time completes with **no exception** but draws nothing. `ThorHudClient` now drives `drainIconQueue` from a no-op `HudElement` registered via `HudElementRegistry.addLast` instead of from its tick handler — the nearest hook guaranteed to run every frame in the right context. Confirmed by first proving vanilla's own `GuiItemAtlas`-based rendering (the real inventory screen) worked fine on the same device/build, which ruled out an environment-level cause.
- **Depth cleared to the wrong convention.** 26.2 uses reverse-Z (near=1, far=0); this class was still clearing depth to `1.0` (the old far-plane value), which put every drawn fragment on the failing side of the depth test. Result: no exception, real quads confirmed present (verified by temporarily logging layer/quad counts through `ItemStackRenderStateAccessor`), a real non-empty GPU readback buffer confirmed all-zero (verified by temporarily logging raw mapped bytes) — and only fixed by diffing against `GuiItemAtlas`/`PictureInPictureRenderer`'s clear call line-by-line and noticing they pass `0.0`, not `1.0`. This was the actual cause of the blank icons; the other two fixes were necessary but not sufficient on their own.

Constraints worth knowing before editing this: must run on the render thread, from inside an active per-frame render pass — see the call-site bug above; a `HudElement` callback satisfies this, `END_CLIENT_TICK` does not. The GPU texture/projection/buffers are static and reused across icons; that's safe despite async readback because the GPU orders `copyTextureToBuffer` against preceding draws.

### Icon request reliability

Icon requests are queued (`MAX_ICON_RENDERS_PER_TICK`) rather than rendered inline, and **every request gets an answer**: a rendered icon, a fallback raw texture, or an explicit failure message (`broadcastIconFailure`, which sends `{"type":"icon","itemId":...}` with no `data` field). Silently dropping unresolvable requests was half the cause of icons appearing inconsistently — the companion app's other half is described in its own CLAUDE.md.

The main (non-client) source set (`src/main/java/com/exojosh/`) is untouched Fabric-template boilerplate and not part of the HUD feature.

## Known unverified/fragile areas (per the handoff doc)

- Package name is settled at `com.exojosh` (main) / `com.exojosh.client` (client), not still in flux as the handoff doc's §3 warns.
- The pre-26.2 note here about unverified Yarn-mapping API calls no longer applies: the 26.1 mappings migration was automated (Loom's `migrateMappings`/`migrateClientMappings`) and every API surface touched by the 26.2 port has since been confirmed against a clean build and, for the rendering pipeline specifically, against real runtime output (see `ItemIconRenderer`'s "Offscreen icon rendering" section) rather than recollection. Anything *not* exercised by that port (code untouched since 1.21.11 and never hit during the icon-rendering investigation) hasn't specifically been re-verified beyond compiling, so treat a compile-only pass as weaker evidence than a comment claiming decompiled/runtime verification.
